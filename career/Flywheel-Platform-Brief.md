## 1. A workspace for the whole project.

I am building Flywheel so people can create software, conduct research, make creative work and learn with AI in one extensible environment.

### The ambition

Bring the editor, models, tools, evaluation, training and project memory together. Keep the work and understanding when the task or model changes.

### The starting point

A public Python engine and native desktop client, with a Windows installer. The complete cross-domain experience is still being built.

Verification supports the product. It is not the entire product.

Sources: [Platform charter](https://github.com/HarperZ9/flywheel/blob/4ac4fbd795b171bae26ca504d6fb5c68bbaa150a/project-docs/PLATFORM-CHARTER.md) | [Windows release](https://github.com/HarperZ9/flywheel/releases/tag/v0.3.11)

## 2. The project should outlast its tools.

The design target is continuity: a person should not have to rebuild their context, explain every past decision or lose useful work when moving between tools.

### Carry the context

Keep sources, decisions, working files and useful lessons connected to the project.

### Make the next step understandable

Show what ran, what changed and what remains uncertain. Let people correct the work and keep going.

### Return time and capability

Help people finish useful work and understand it. Learning belongs in the product, not just its onboarding.

Product hypothesis informed by independent use. Customer pain and willingness to pay still need validation.

Sources: [Product and implementation](https://github.com/HarperZ9/flywheel)

## 3. There is working software to build on.

The implementation is more than a proposal. Its maturity varies by component.

### Released desktop

Flywheel v0.3.11 has a public Windows installer, published September 4, 2026. Release availability is verified; this brief does not claim a new installation test.

### Implemented engine

The Python engine routes tasks, checks tool requests, records runs and serves a local gateway. The Flutter client provides the desktop interface.

### Additional building blocks

Project-memory APIs, trace-derived evaluation tasks and branching creative-image workflows are present in source. That is not proof of a finished cross-domain workflow.

Current use is independent development. No external Flywheel customer deployment is established here.

## 5. Prove the experience with real work.

A proposed 6–12 month funded program would turn the existing components into an integrated product tested with external design partners.

### Engineering and applied R&D

Carry a project from investigation through a tested change and a reviewable handoff.

### Research teams

Carry sources, experiments and conclusions forward without losing their limits or history.

### Creative production

Carry a brief through asset variations, comparison and revision, preserving the choices behind the result.

These are candidate customer programs, not signed pilots. Select the first with a willing buyer; expansion remains part of the company thesis.

Sources: [Explore the product](https://harperz9.github.io/flywheel.html)

## 6. Earn the reason to switch.

The case is the complete working experience, not a claim that nobody else has memory, evaluation or local models.

### Compare the actual workflow

Use the same project with the team's existing tools and Flywheel. Count useful completions, mistakes caught, setup time, review effort and recovery after interruption.

### Test whether knowledge carries forward

Return to the project after changing a model or contributor. Check what survives and how much explanation must be repeated.

### Let repeat use settle the question

Look for paid use, return use and expansion into another workflow. If integration costs more than it helps, change the product.

Proposed comparison, not a completed benchmark. No measured advantage or product-market fit is claimed.

Sources: [Inspectable implementation](https://github.com/HarperZ9/flywheel)
