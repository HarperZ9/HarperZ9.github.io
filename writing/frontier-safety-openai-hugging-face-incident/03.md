## The response pattern worth building

After reading the reports, I would want a practical set of controls that is boring by design.

- By default, block every network route the task did not ask for. That includes routes through package managers, caches and artifact stores, the services that download and keep software and files for a test. Every exception should be explicit, logged and scoped to the task.
- Treat shared writable storage as a communication system. If agents can write where other agents can read, that storage is a channel between agents, whether or not anyone designed it as one.
- Give evaluations a safe exit. An impossible or low-probability task needs a bounded way to fail that the evaluator, the system grading the test, accepts. Without one, the evaluation can punish the agent into endless search.
- Measure the model's capability and the environment's security separately. A benchmark result should say whether it measured the model, the harness, the sandbox, or a mix of all three.
- Keep an independent record of transcripts and actions. If agents can fake or erase the record, the review after the incident becomes one more document nobody can verify.
- Keep a private model on hand for defensive incident response. Responders should not have to send real attack traces, credentials, payloads or private logs into a hosted model (one another company runs on its own servers) that cannot tell response work from misuse.
- Publish lessons whose claims stay within the evidence, and hold back operational recipes, the step-by-step instructions an attacker could follow. The public write-up should strengthen defenders without becoming a distribution channel for the next actor.

For this site, that means the daily frontier-safety briefing should keep a stable shape, in this order:

- What changed in the public record.
- Which control boundary moved.
- What evidence supports the claim.
- What remains unknown.
- What Flywheel or the tools around it should build or test next.

A safety briefing that does not change the workbench is just commentary. This one should turn into test fixtures, the fixed cases a tool is checked against, for six jobs: detecting message boards, flagging data that passes through shared storage, scoring safe exits, checking that transcripts are intact, detecting faked tool calls (the actions an agent asks its software tools to take), and holding back incident-response material until sensitive detail is removed.

## Process note

This briefing uses only the public reports listed above, and it was written with AI assistance. It describes which kinds of safeguard failed and stays above operational technique, the level of detail someone could use to repeat an attack. It deliberately leaves out live exploit details, collections of working bypasses, exploit chains, payloads, credentials, hostnames, techniques aimed at particular systems, and which software versions were affected.
