## A working map of the tools

The portfolio grew out of different kinds of work. Some tools have their own command-line interface, a program you run by typing commands, and their own release. Some are libraries, code meant to sit inside another application. Others are research or creative projects with a smaller public demonstration. Flywheel is meant to gather the useful connections in one place and still keep separate ways into the tools that stand on their own.

The map below explains the public product families and what each one does. It follows the [published product records](https://harperz9.github.io/overview.html), and source links are available from each record. A public description tells you what a project claims to offer; running the current release on a suitable task is a further check. The descriptions here keep each tool's important limits, and where they propose a research use, it stays a proposal. The map is reference material, so a reader following the argument can skip ahead to [What has to survive the connections](#what-has-to-survive-the-connections).

### Flywheel: the application through which work runs

[Flywheel](https://harperz9.github.io/flywheel.html) takes a task, a chosen route to an AI model and a set of tools, and then coordinates the run. Its Python engine and its native desktop app are two ways into that work. Optional sealed receipts for each tool call let someone inspect and recheck the recorded operations offline. For a reviewer, the useful question is what happened during this particular run, with this model and these permissions.

I intend Flywheel to be a central harness for coding and AI agents, meaning the program that runs a model with its tools, and I want it to support evaluation, research and other workflows too. A tool that is useful on its own should stay available without the whole application. Inside Flywheel, the same tool should show up where its job is needed: a researcher gathering sources should meet the source-intake tool, and a reviewer should meet the evidence and its limits. The current releases and the installed desktop app can differ. So a change in the source code needs installation and workflow checks before it becomes a claim about the application people use.

### Forum: organizing dependent work

[Forum](https://harperz9.github.io/forum.html) turns a request into tasks that depend on each other. It can run independent tasks at the same time through local commands or model APIs, the interfaces programs use to call a model. It can pause where a person has to approve the next step and resume a run that was interrupted. Its ledger, a running log, keeps a record of the orchestration that can be replayed. That helps when one agent's result feeds another agent and an interruption would otherwise lose the link between them.

Forum's job in Flywheel is coordination. Its record can show which task ran and what that task recorded. Judging whether each result is right still needs the evidence for that task. Agents working in parallel can split the work. When they agree, their agreement carries the limits of shared dependencies that I discuss later in this essay.

### Relay: carrying a coding session across model routes

[Relay](https://harperz9.github.io/systems/relay.html) is a coding agent whose actions pass through permission checks. It can reach local models, subscription command-line tools, APIs and gateways, which are services that pass requests on to a model. It supports resumable sessions, failover to another route, acceptance checks and a hash-chained session record. In a hash-chained record, each entry carries a fingerprint of the one before it, so changing an earlier entry means every later fingerprint has to change too. A developer can use Relay when the work should survive a change of model endpoint, the address where a model is reached, and still keep the account of what was tried.

Relay overlaps with part of Flywheel's work. The integration needs one clear owner for session state and permissions, so two agents never each assume the other one enforced them. Relay's list of blocked commands is a convenience. It gives no general guarantee of containment, which would mean keeping an agent inside set limits. A useful evaluation would interrupt a run at a moment that matters, then inspect the recovered state and look for any action that ran twice.

### Canon: taking continuity to another host

[Canon](https://harperz9.github.io/canon.html) turns local memory records and typed information that someone has explicitly selected into continuity capsules. Typed information here means structured data whose fields have declared types. A capsule is a package of chosen context that another AI tool, called the host, can load. Canon previews whether the target is ready. It exports Markdown or structured JSON for hosts such as Codex and Claude Code. When the caller picks a local instruction file that it owns, Canon changes only the regions declared for it.

This deals with the work that disappears when a person switches tools or starts a new session. Canon's role in Flywheel is moving chosen context, with the target and the changed region visible. It ships publicly through GitHub at the recorded release point. A capsule needs a review of its contents and permissions before it enters a new host, since being portable says nothing about whether every instruction it carries belongs there.

### Mneme: retrieving memory with its history

[Mneme](https://harperz9.github.io/systems/mneme.html) stores conversation turns and imported source items in a local SQLite database, a small database kept in one file on your own machine. It has a command-line tool and an MCP interface. MCP, the Model Context Protocol, is a common way for AI tools to call other programs. Both return what they retrieve along with its provenance, a record of where each item came from, plus recall receipts and history views. Mneme can rank results by a mix of text relevance, vector similarity (a numeric measure of how close two passages are in meaning) and recency. Its records of what it updated and what it forgot let a maintainer see how stored material changed.

Mneme helps with one question: “where did this remembered claim come from?” Canon helps move selected continuity into another host, a related job with its own inputs and outputs. When Flywheel recalls an item, it should keep the source next to the text, along with any drift or gap. In the published account Mneme owns its own source recheck, and an independent reread by Crucible is a separate integration requirement.

### Bulletin: shared agent work that people can inspect

[Bulletin](https://harperz9.github.io/systems/bulletin.html) is a public board that AI agents can read and write over HTTP or MCP. A signing key identifies who posted. Posts and attachments are served as untrusted input. Inbox acknowledgements record which delivered page a reader says it handled. People can inspect the shared work through the [board interface](https://harperz9.github.io/bulletin.html).

I want Bulletin to help with reporting findings, handing off work and correcting claims in public. It can also supply an environment for a carefully specified study of how agents coordinate. The board shows what was posted through it; it does not show everything that happens in other applications, prove what influenced a model, catch every malicious instruction or contain an agent. A study would show more than watching a lively conversation, and it would need to record the exact messages each agent received, keep the grader (the automated check that scores an agent's work) separate from the board and compare outcomes under declared conditions.

## Finding material and understanding its structure

### Index: a map with locations to inspect

[Index](https://harperz9.github.io/index-graph.html) reads a code repository's manifests, the files where a project describes itself and what it depends on, along with its imports, symbols and local documentation. From these it builds dependency maps, offline wikis, context packets and inventories of a workspace, each backed by file-and-line evidence. Background jobs handle larger scans and recovery. A user can start with a question such as where a feature lives, then follow the map back to the code.

Index's role in Flywheel is to make the choice of context more deliberate, since a good map means less need to send a whole repository to a model. Imports that load at run time and structures the scanner does not support can stay incomplete, so the map has to keep those limits visible. A missing connection may mean the scanner could not resolve it, so someone has to inspect the source before it becomes a conclusion about the architecture.

### Gather: capturing the source material

[Gather](https://harperz9.github.io/gather.html) collects material into a corpus with provenance, where each item is stored under a fingerprint of its own content. It takes in documents, PDFs, scholarly records, feeds and media, and uses a browser or an API for sources that need one. A researcher hands it sources and gets back stored items whose origins can be checked again later.

Gather belongs before a synthesis or claim check. The intake route matters. A static web capture does not run JavaScript, and a media transcript can leave out what appears in a frame of video. A successful connection also has to produce a nonempty capture of the expected material. Those capture details should travel with the excerpt through Flywheel, where a summary should never hide them.

### Chorus: examining a captured discussion

[Chorus](https://harperz9.github.io/chorus.html) takes a captured thread or a set of comments and produces written summaries, which Chorus calls digests, that group and weight the discussion. Those summaries can be rechecked. Its review of source changes helps show whether gathered material still matches a reference set. A researcher can use it to study recurring themes without letting one hand-picked comment stand for the whole discussion.

Its sentiment component handles English only and reads it literally, so it can miss sarcasm and context. A summary is also limited by how the corpus was chosen. For Flywheel, the useful handoff runs from the material Gather captured, to the Chorus synthesis, and back to the original excerpts. A frequency or weight inside that corpus should never turn into a claim about a whole population.

### Plexus: finding possible tool connections

[Plexus](https://harperz9.github.io/systems/plexus.html) reads tool manifests, the files where tools describe their inputs and outputs. It finds connections that the tools declare as compatible and can produce dependency graphs or pipeline scripts that run. It probes the tool routes registered in Flywheel only when someone asks.

This gives a starting point for standard interfaces, because Plexus can tell a builder that one tool declares an output that another tool accepts. A working integration also has to agree on how errors, cancellation, authentication, source locations and version changes behave. A declared connection needs a real test run before anyone presents it as working, most of all when a pipeline includes an action with real consequences.

## Checking a result and accounting for an action

### Crucible: testing an explicit claim

[Crucible](https://harperz9.github.io/crucible.html) breaks a thesis into separate claims, each with a stated condition under which it fails, and checks those claims against the evidence or measurements supplied. It returns a record that can be recomputed, with the result `MATCH`, `DRIFT` or `UNVERIFIABLE`. The user has to say what the test examines and what would count against the claim.

Crucible helps when a task can be made precise enough to test. Its result depends on the evidence supplied, the way it was measured and the criterion chosen. In Flywheel, it can help keep a model's confident message that it finished from being the only acceptance check. The criterion still needs scrutiny of its own, including a wrong example that the checker must reject.

### EMET: preserving a narrow integrity statement

[EMET](https://harperz9.github.io/emet.html) supplies the byte-level comparison described earlier. It fits into a pipeline wherever a later reader needs to check that the material still agrees with its declared anchor. It can support source intake, review and later replay, and its verdict keeps the same narrow scope throughout.

The work needed at each connection is about meaning: whatever uses the result has to keep what the result means. A source can arrive byte for byte and still contain a falsehood. An intact authorization record can fall outside the scope of a new action. The tool around EMET has to carry the extra checks without quietly enlarging EMET's claim.

### Service Desk Incident Environment: a bounded workflow to evaluate

The [Service Desk Incident Environment](https://harperz9.github.io/flywheel.html#service-desk) provides synthetic incident workflows, built from invented data. It compares the claims an agent recorded with task outcomes it recomputes, and in an offline HTML report it points out contradictions between what was authorized, the responses given and what was changed. An evaluator then has concrete changes in state to inspect and does not have to rely entirely on the agent's own account of success.

The released environment is an add-on. It needs a compatible Flywheel engine. It is a useful, bounded example of the direction of this work: choose a workflow, define the expected behavior and inspect the state that results. It supports no general conclusion about behavior in a real production service desk, or about whether a model is aligned, meaning whether it reliably does what its developers intend. A production pilot would need its own data permissions, failure cases and acceptance conditions.

### Model Provenance Validator: checking the evidence record's shape

[Model Provenance Validator](https://harperz9.github.io/security-toolkit.html#model-provenance-validator) checks JSON records that tie a claim about a model or a release to its sources, retrieval dates and publication status. It can produce a Proof Surface packet and redact output that looks like a credential, and a release reviewer can use it to find missing or malformed fields before working on the claim itself.

It does not fetch the cited source or decide whether the claim is true. In a Flywheel release workflow it can validate the record a reviewer receives, and comparing the sources and assessing safety stay separate, named tasks.

### Repo Proof Index: making evidence navigable

[Repo Proof Index](https://harperz9.github.io/security-toolkit.html#repo-proof-index) scans proof packets, receipts and contracts. It builds an index of each one's type, status, evidence summary and source path, and it validates the packet formats it knows. A reviewer can use that index to find the artifact that bears on a question.

The index cannot show that the evidence is enough. It leaves unread the private payloads a record points to. Linked to Flywheel, the index should cut the time spent finding things and keep missing evidence in view. A private reference needs an authorized route for review, or a plain statement that this review could not see the source.

### Proof Surface: structured records for review

[Proof Surface](https://harperz9.github.io/proof-surface.html) validates structured records of workflows, delegation, authorization and witnessing. Its library and command-line tool build evidence packets and return verdicts or advisory decisions such as allow, deny and needs-human. The packet gives other components one common structure to inspect.

Enforcement belongs to the system around it. Producing an advisory result does not make Proof Surface run an action or grant permission. When Proof Surface is integrated with Flywheel, the component that is about to act has to check the current request against an accepted authorization and keep the exact target.

### Accountable Surface: the execution boundary

[Accountable Surface](https://harperz9.github.io/accountable-surface.html) puts approval checks around the file, command, web and browser actions it supports. It can pause or block a request, inspect what happened and try to roll back a failure that can be reversed. A hash-chained journal records its decisions and observations.

This is the part of the portfolio concerned with carrying permission into execution. A model cannot authorize itself. The journal also needs checks at the adapter, the small piece of code that performs an action on one kind of system. Changed inputs, a stale approval and an uncertain response each have to stay a separate case. Any claim about enforcement reaches only as far as the supported adapters and their tests.

## Privacy and release hygiene

### Phantom: inspecting exposed machine identity

[Phantom](https://harperz9.github.io/phantom.html) inspects the hardware identifiers that a Windows or Linux system exposes, on systems you own or are expressly authorized to examine. The changes it supports come with backup and restore paths, and the public product covers one layer of these identity surfaces. Work at the kernel and firmware level, the deepest layers of the operating system and the machine's startup code, is modeled in the product, and no end-to-end shipped claim is made for it.

I want to extend this work toward a wider privacy boundary, including protection for confidential intellectual work. That is a direction of development. Changing a machine identifier cannot, on its own, protect the contents of a prompt, a file or a provider's log. A privacy workflow that works needs explicit decisions about what leaves the machine, where it goes and what the receiving service keeps, and each of those is a separate control to design and test.

### behavior-transform.io: a local I/O wrapper

[behavior-transform.io](https://harperz9.github.io/systems/behavior-transform.html) wraps local file operations, subprocesses, HTTP fetches, manual input and MCP traffic. Depending on the declared mode and local text rules, it passes content through or transforms it. It records values such as hashes, counts of substitutions and return codes.

A wrapper like this makes changes to the traffic it wraps an inspectable part of the workflow. A transformation can also change meaning or hide context, so whatever consumes the output needs to know it happened. The public record has no tagged release and no independently verified entry command. Linking it to Flywheel would need a concrete contract for transformations, with tests that keep the information a reviewer needs.

### Secret Redact IO: reducing accidental disclosure

[Secret Redact IO](https://harperz9.github.io/security-toolkit.html#secret-redact-io) is a helper library that redacts output from file reads, fetches, writes and subprocesses, and emits receipts that hold only hashes. It can support an adapter that has to record an operation without copying sensitive values into its log.

Redaction rules can miss a secret or remove material someone needs to interpret a result. So redaction should come with collecting less data in the first place and with an explicit review of output. A redacted receipt is limited by what it leaves out. It cannot stand in for the source value when a reviewer needs that value to settle a claim.

### Public Surface Sweeper: checking a release handoff

[Public Surface Sweeper](https://harperz9.github.io/public-surface-sweeper-sample.html) checks a repository or portfolio before publication for missing public files, unclear README handoffs, strings that look like credentials, and release metadata. It can check whether proof packets are ready and whether delivery has drifted. It is a practical check for the moment internal work becomes something another person downloads or reads.

Its scope is release hygiene. It does not replace an analysis of dependency vulnerabilities or a security review. In Flywheel, it can become one explicit step before publication, with a report of what it checked and what fell outside the scan.

### Agent Hook Pack: checks at recurring workflow points

[Agent Hook Pack](https://harperz9.github.io/security-toolkit.html#agent-hook-pack) installs hooks, safe to share publicly, that check for secrets, guard branches, keep environments in sync and keep a repository tidy. A hook puts a check at a point where a developer might otherwise forget it.

The public package leaves out private policy layers. Each host runs hooks in its own way. An installation has to be verified in that host. The useful version is a small, visible check with a failure you can recover from. Each hidden startup instruction added to the pile makes that harder to keep.

## Toolmaking, learning and creative practice

### Telos: a workbench with its own automation tools

[Telos](https://harperz9.github.io/systems/telos.html) is a local workbench with command-line and MCP interfaces that runs workstation checks, simulations, research proofs and experiments with models or learning. Its public record also includes automation for the browser and for Windows. Each run produces a receipt that can be rechecked.

That automation work should be assessed before anyone builds another layer for controlling a computer. For Flywheel, the practical question is which Telos adapter can perform a needed action, under which permissions, and with what result someone can observe. Interfaces before version 1.0 can change. Having an automation interface proves neither that it beats another tool nor that the currently installed integration has been accepted.

### BuildLang: explicit permissions in a compiled program

[BuildLang](https://harperz9.github.io/buildlang.html) is a systems programming language with its own compiler. Each program declares what it is allowed to touch. The compiler checks those permissions and the memory rules, then produces native code by way of C. The project includes C interoperability, editor support and build receipts that can be rechecked. Its other output backends are still experimental.

BuildC is also part of the planned toolchain, though the current public map does not establish it as a separate released product. I still want the toolchain to serve more of the portfolio. For now, the work continues where it already lives, by extending the existing Python, C++, Rust and other implementations. Claiming that BuildLang outperforms Rust would take equivalent programs, compiler settings and hardware, plus measured results. This essay makes no such performance claim.

### Learn: supporting the learner's own work

[Learn](https://harperz9.github.io/learn.html) plans study sessions from stated goals and attempts the learner writes, and it rechecks them. It includes spaced review, retrieval prompts, checks on prerequisites, tracking of misconceptions, prediction and self-explanation. Course logistics run on a separate route, which stops at graded work and other steps that need consent.

The planned link to Flywheel is a learning workflow where the person stays responsible for the attempt and can inspect the feedback. A record of completed prompts does not show that the person retained or understood anything. The education section below describes the further evidence I want these tools to help produce.

### Studio Engine: a reusable scene description

[Studio Engine](https://harperz9.github.io/systems/studio-engine.html) generates shader visuals, audio and motion from a scene description that can be reused. A local command-line tool and HTTP interface can render PNG frames that come out the same every time, and they record hashes for the generated scene. A creator can change one declared input and inspect the output that changes with it.

It is still unfinished as a product. Its value to the wider tooling is creative work that can be reproduced, since the scene and render settings give another person something to run. Output that repeats exactly helps compare revisions. Artistic quality still needs human judgment.

### Build Color: working with digital color

[Build Color](https://harperz9.github.io/build-color.html) converts, compares and transforms digital color, the numbers a computer uses to describe a color. Its technical scope covers perceptual color spaces, tone mapping, chromatic adaptation, gamut mapping, ICC profiles and lookup tables, with an optional graphical interface.

Technical artists and developers can use it to see what a color transform does. It works on digital values. Measuring a physical display needs a real instrument and a suitable procedure. A link to a renderer should keep the chosen color space and transform settings, so someone can investigate an image that looks wrong.

### Calibrate Pro: connecting a display change to its evidence

[Calibrate Pro](https://github.com/HarperZ9/calibrate-pro) is a toolkit for calibrating displays on Windows. It finds displays, prepares calibration targets and works with monitor controls, profiles and lookup tables through a preview-and-confirm workflow. The graphical app proposes a supported change to the display, and a person inspects it before applying it. Its reports keep track of whether each value was measured, estimated, simulated or not measured at all.

It is a separate tool that goes beyond the product list in the current public overview. Its source describes a 2.0.0 installer and a portable package. The Windows files are unsigned. A reading from an instrument and an estimate made without a sensor carry different weight as evidence. It could link to Flywheel as a creative workflow someone can review. A source link between two projects does not establish an installed Flywheel integration. The [pinned product description](https://github.com/HarperZ9/calibrate-pro/blob/3d24d16d6b57b2264ac122b15a6b64530cefed26/README.md#L18) and [workflow boundary](https://github.com/HarperZ9/calibrate-pro/blob/3d24d16d6b57b2264ac122b15a6b64530cefed26/README.md#L61-L66) let a reader inspect those distinctions.

### Retro Engine, Gallery and Loom: visible creative work

[Retro Engine](https://harperz9.github.io/retro.html) is a studio that runs inside the browser for images, drawing, shaders and audio traces. It applies effects such as old hardware palettes, dithering and CRT screen processing, and it can export to [Loom](https://harperz9.github.io/loom.html) or hand work off there. [Gallery](https://harperz9.github.io/gallery.html) is a public display page that sits next to it.

These pages show another use for the infrastructure: making and sharing work that people can see and hear for themselves. A useful handoff keeps enough settings to continue editing somewhere else. Each export route still needs its own acceptance check. An image with a retro look is no evidence that a historical rendering engine was restored correctly.

### Engine Revival and BRender Archival: preservation with attributable evidence

[Engine Revival](https://harperz9.github.io/engine-revival.html) builds and audits metadata about restoring historical engines, in a form safe to publish. It can generate a build scaffold for BRender that sits outside the original source tree. [BRender Archival](https://harperz9.github.io/brender-archival.html) takes on a narrower task. It rebuilds the public Argonaut BRender source, runs the restored native code, captures renders, and packages the resulting scaffold and evidence without copying the upstream source.

This work offers a useful discipline for the wider portfolio: give the reader the input, the transformation and the result behind each specific statement. For a preservation claim, metadata and a generated build scaffold have to be labeled as what they are, and evidence that restored behavior works comes from the real historical code and a record of it running.

### The graphics runtime family

Elder ENB and Truth ENB change how the game Skyrim looks, and the projects around them are technical graphics work whose terms name standard parts of game and rendering software. [Elder ENB](https://harperz9.github.io/elder-enb.html) is a shader suite for Skyrim, with quality tiers, bounded cinematic effects and optional native support. [Truth ENB](https://harperz9.github.io/truth-enb.html) is a separate shader suite built around computed atmosphere, clouds, exposure and tone mapping. Each has its own look and its own implementation choices. Acceptance in the live game and in the ENB host remains a release boundary. Truth's public upload is waiting on its required acceptance matrix.

[ENB Runtime Core](https://harperz9.github.io/enb-runtime-core.html) is an embedded C++ library. It identifies an ENB host that is already loaded, validates its SDK interface and coordinates callbacks and behavior around saved games. [SkyrimBridge](https://harperz9.github.io/skyrimbridge.html) exposes game state, and operations on records or assets, through a versioned interface with an optional rendering tier. Its default public build leaves out the native replacement suite.

[RAW](https://harperz9.github.io/raw.html) is a D3D11 rendering platform with frame capture, GPU diagnostics, shaders that reload while it runs, and effects applied partway through a frame. Its source is public and active. No public release is claimed. These projects are concrete graphics and systems work, and their link to Flywheel could be a workflow for building, inspecting or catching regressions. Their existence establishes neither a single installed graphics product nor any result about alignment.

## The controlled-private systems and older names

Some tools have public descriptions while their code and operational evidence stay private. The [private-practice index](https://harperz9.github.io/private-practice.html) states that boundary. These tools can be explained at the level already published, without releasing sensitive methods and without implying that a public description of a capability is a product you can download.

[Array](https://harperz9.github.io/array.html) coordinates authorized security-assessment campaigns, with scoped approvals, supervised work and an evidence ledger. [Seed](https://harperz9.github.io/seed.html) is a native engine for security assessment and detection engineering, the work of writing rules that spot attacks, and its public material includes synthetic demonstrations and a stated scope for the work. [ORCA](https://harperz9.github.io/orca.html) manages how assessments run, along with findings, reports and the provenance of each release. These descriptions name each tool's separate responsibility. Using any of them requires a defined, authorized engagement and an approved recipient for the results.

[Sofer](https://harperz9.github.io/sofer.html) is the private runtime that orchestrates that practice, managing campaign state, correlation, reporting and the staging of disclosures. [Gate](https://harperz9.github.io/private-practice.html#gate) is its subsystem for release checks. Before work advances, it validates the required manifests, source and test paths, controls and the results of verification commands. A release check covers the scope and recipient it reviewed and cannot supply authority for a different operation.

[Bounds](https://harperz9.github.io/bounds.html) checks agent actions, runtime observations and release candidates for drift from the stated intent, unsupported claims, exposure and failed test fixtures. [Isomorph](https://harperz9.github.io/isomorph.html) studies classifier and refusal behavior at inference boundaries it is authorized to test, with controlled trials and records of the results. A classifier here is an automated filter that sorts or blocks content, and an inference boundary is the point where a model receives a request and answers it. A restriction seen in one configuration needs its conditions stated. The public description supports neither a conclusion about a model's general disposition nor permission to test an unrelated service.

[Kun](https://harperz9.github.io/kun.html) keeps local information for recovering access to systems you own. It uses path references, redacted diagnostics, rotation notes and runbooks, which are written step-by-step procedures. It records where the authority to recover lives. It keeps no raw credentials. That makes it relevant to continuity after a failure, while secret material stays out of public evidence.

The older [Aleph route](https://harperz9.github.io/aleph.html) now presents Checkpoint, an entry to controlled private work that describes it only at the level of purpose. The older [WARDEN website route](https://harperz9.github.io/warden.html) points to Proof Surface. Sofer's command-line tool also uses the name WARDEN. When you read older records, the project context matters. Renamed pages, internal forks and archived predecessors should not inflate the product list.

The possible link to Flywheel is a narrowly authorized workflow with a clear boundary for review and disclosure; a shared workspace alone does not make these tools ordinary public Flywheel modules. A public report can explain the question, describe the method at a suitable level and give a scrubbed result, one with private details removed. The protected operational evidence stays with its authorized recipient.

Typography and other studio experiments remain part of the portfolio's history. The current priority is Flywheel and the tools that support it. Additional names in the wider program, including BuildDB and BuildQL, still need a verified public product description and release boundary before this essay can explain them to the same standard. Private artifacts stay outside the inventory. This map covers the published descriptions of products and capabilities, and it makes no claim that every local project has been audited.

## What has to survive the connections

In one proposed use, an evaluator gathers an incident report with Gather, the source collector, finds the relevant adapter with Index, the code map, and gives Flywheel a bounded task: reproduce the incident. Forum, the coordinator, may split the independent checks. Crucible, the claim tester, can test a stated property of the result, and EMET keeps the scope of an integrity comparison. Mneme, the memory store, can keep the finding with its source, and Canon can carry selected continuity into another host. A scrubbed account could then be shared on Bulletin, the public agent board.

Every handoff in that example needs an explicit contract. The receiving tool needs the version of the source, the selected value and what the result means. A request to share material needs an authorization tied to its destination. A cancellation or an uncertain response has to survive the handoff and must never turn into a success label. The example describes the integration I am aiming for; the essay does not claim that anyone ran and accepted this whole chain for the article.

How much the central application is worth will depend on how well it keeps this context while making the task easier for a person to finish. MCP and HTTP APIs give these tools ways to talk to each other. A shared transport still leaves questions open at the level of the application: what an empty result means, how a partial capture is shown, which convention counts positions in text and what happens when the schema version changes. Standard interfaces should settle these points with small examples and with controls built to fail on purpose.
