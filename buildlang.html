What a function may do belongs in its type.

BuildLang is a systems programming language in which a program declares what it is allowed to touch. The compiler checks those declarations and its memory rules, then emits native code through C. It ships with a CLI, editor support, two-way C integration and experimental shader output.

It is for systems programmers who want the compiler, not a comment, to say what each function is allowed to do.

buildc · buildlang 1.2.0 on crates.io · effects and lifetimes, in the type

What it does

In most languages a function can open a file or call the network and nothing in its signature says so. In BuildLang each function lists the effects it may perform. If it performs one it did not list, the program does not compile, and the error points at the line. Memory lifetimes are part of the type too, so a function cannot hand back memory that may be freed sooner than promised.

The signature says what a function may touch and whose memory it returns, and the compiler checks both.

Examples with real compiler output

Each of these is a real file checked by the real binary: buildc, the release binary. The output is verbatim.

Exhibit I BuildLang · effects are part of the signature
fn load_config() {
    read_file("ops.toml");        // reaches the filesystem
}

$ buildc check missing_effect.bld
function `load_config` performs effect `FileSystem` but does not declare it
  help: add ~ FileSystem to the signature
  note: capability `FileSystem` was triggered by ambient call(s): read_file

# declare the effect, and the same check passes, then writes a receipt
fn load_config() ~ FileSystem { read_file("ops.toml"); }

$ buildc check load_config.bld --receipt receipt.json
Type checking... OK
  "declared_effects":      { "load_config": ["FileSystem"] }
  "observed_capabilities": { "load_config": { "FileSystem": ["read_file"] } }

Reading a file without declaring it fails to build, with the error on that line. Declare it and the check passes, and --receipt writes the declared effects next to the observed ones.

Captured from buildc check (Rust toolchain, release build).

Exhibit II BuildLang · memory has an owner, and the type tracks it
fn pick<'a, 'b>(x: &'a i32, y: &'b i32) -> &'a i32 {
    y          // returns 'b where the signature promised 'a
}

$ buildc check pick.bld
Lexing... OK (28 tokens)
Parsing... OK (1 items)
Type errors found:
  function returns `&'b i32` but expected `&'a i32`

The function promised to return memory with lifetime 'a and returned memory with lifetime 'b, which may end sooner. The compiler rejects it.

Diagnostic from compiler/src/types/error.rs, through the lifetime matching in unify.rs. Lifetimes are tracked across function calls; checking at every call site is not finished yet.

Exhibit III BuildLang · checked, then compiled to native
# an algebraic effect with a handler: parsed, effect-checked,
# lowered to C, compiled, and run:
$ buildc run examples/quickstart/effects_greeting.bld
Hello, teammate!

The program is parsed, effect-checked, lowered to C, compiled and run.

C is the production backend. LLVM, WASM, SPIR-V, x86-64, ARM64 and Rust output are experimental.

Exhibit IV BuildLang · it speaks C, both ways
# name a C library by its header and link flag, then call straight in:
extern "C" link "sqlite3" header "<sqlite3.h>" {
    fn sqlite3_libversion() -> &str;      // the header stays authoritative
}
fn main() ~ Foreign { let v = sqlite3_libversion(); }

$ buildc build examples/ffi --emit c
[4/4] Code generation (c)... OK (53517 bytes)

# in the emitted C, verbatim:
#include <sqlite3.h>          // your header, included as-is
// buildc-link: sqlite3       // recorded, so `buildc build` links it
_1 = sqlite3_libversion();    // the real call into the C library

# the reverse is `extern "C" fn` (C calls BuildLang). and a live run
# straight through a C variadic:
$ buildc run examples/variadic/main.bld
the answer is 1 and 2

Name a C library by its header and link flag, and BuildLang includes the header, records the link, and calls straight in. extern "C" fn goes the other way, so C can call back. A foreign call is still an effect: main declares ~ Foreign, so reaching into C sits behind the same check as touching a file.

Captured from buildc build --emit c and buildc run (release build). The final native link against sqlite3 uses your own C toolchain.

Numeric kernels with checked invariants

For numeric code, buildc run --emit-receipt runs a .bld kernel, captures its output series, checks a stated invariant (a rule the numbers must obey) and writes a JSON receipt. buildc receipt verify runs the program again and recomputes the verdict, so a changed number, an edited receipt or a changed source each fail with their own error. buildc receipt export verifies and then sends the measurements to Crucible.

The verdict covers the output series of the compiled program, and each receipt is labelled NOT_A_NEW_PHYSICAL_LAW.

Exhibit V BuildLang · run a kernel, seal a receipt, re-derive the verdict
# a heat-diffusion kernel: its energy should never climb. run it,
# check the invariant, seal a receipt:
$ buildc run heat.bld --emit-receipt heat.json --invariant energy-monotone
Running... OK (240 steps captured)
Invariant energy-monotone... HELD
  "label":     "NOT_A_NEW_PHYSICAL_LAW"
  "verdict":   "HELD"   // witnesses the OUTPUT SERIES, not the PDE

# re-run from scratch and re-derive the verdict. change a number and it fails:
$ buildc receipt verify heat.json
Re-running program... OK
Re-deriving verdict... MATCH       # drift / tamper / source-change each fail typed

Verify re-runs the program and computes the verdict again, so a changed number, an edited receipt or a changed source each produce their own named failure.

Captured from buildc run --emit-receipt and buildc receipt verify (release build).

Exhibit VI BuildLang · eight invariants, each with a kernel built to pass and one built to fail
# every invariant ships paired: a kernel that should HOLD and one that
# should VIOLATE, so a verdict of HELD actually means something.
energy-monotone    # the series never climbs past tolerance
conservation       # stays within roundoff of its starting value
bounded            # never exceeds the initial value (a discrete maximum principle)
energy-identity    # per-step energy balance holds to roundoff
                   // the FTCS analogue of d/dt ∫u² = -2a ∫u_x²
relation --columns N  # N reported columns must agree, so a run can't hide a divergence
conserved-band     # approximate conservation inside a fixed error budget
non-negative       # an absolute floor: no value drops below zero
cross-backend      # C and Rust backends run the same kernel and must agree

# conserved-band grounds symplectic integration, and it shows the point:
$ buildc run leapfrog.bld --emit-receipt lf.json --invariant conserved-band
Invariant conserved-band... HELD    # energy stays in an O(dt²) band
$ buildc run euler.bld    --emit-receipt eu.json --invariant conserved-band
Invariant conserved-band... VIOLATED # explicit Euler drifts out and fails, as it should

Each invariant has a matched pair: a kernel meant to hold and one meant to break, at a fixed tolerance, so the check is shown failing as well as passing.

Eight invariants: energy-monotone, conservation, bounded, energy-identity, relation --columns, conserved-band, non-negative and cross-backend. Each has a passing and a failing kernel except cross-backend, which has one kernel run on two backends. The leapfrog and Euler runs show conserved-band telling a stable integrator from a drifting one.

Exhibit VII BuildLang · export witnessed measurements to Crucible
# re-verify, then hand witnessed measurements to Crucible (the Telos bridge):
$ buildc receipt export heat.json --to crucible
Re-verifying... OK
Emitting witnessed measurements... OK
  "witnessed": true   // re-derived here, not trusted from the file
  "label":     "NOT_A_NEW_PHYSICAL_LAW"

Export verifies first, then sends the measurements to Crucible with the same label.

C is the production backend; HLSL and GLSL cover shaders; SPIR-V, LLVM, WASM, Rust, x86-64 and ARM64 are experimental. The eighth invariant and the receipt chain landed after the crates.io release, so build from source to try them.

Tests and current state

Built in Rust. cargo test in compiler/ passes 1,605 tests, with 0 failed and 11 ignored. The scientific-runtime receipt corpus passes 27 of 27, and the runnable C-backend corpus passes 8 of 8.

Recent additions: two-way C interop, opt-in linear types and a first step toward automatic memory cleanup.

BuildLang calls C libraries by header and link flag and exposes functions as extern "C" so C can call back, all through buildc build. Linear types, an opt-in no-cloning rule, are experimental. Automatic memory cleanup is opt-in and narrow. Concurrency is parsed and type-checked, but its runtime is not in compiled programs yet, and the self-hosting compiler does not run yet.

Install and run

Install with cargo install buildlang from crates.io, with a C compiler on your PATH, or build from source. buildc doctor checks that the C path is ready. Then run the examples, or write a function that touches a file without declaring it and watch the build fail.

$ cargo install buildlang            # from crates.io; installs the buildc binary
# or from source:
$ git clone https://github.com/HarperZ9/buildlang && cd buildlang/compiler
$ cargo build --release

$ buildc doctor                       # toolchain + C-backend readiness
C backend: ready

$ buildc run examples/quickstart/effects_greeting.bld
Hello, teammate!
