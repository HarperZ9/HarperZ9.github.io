What Flywheel is

Flywheel is an AI workstation and coding harness, the program that runs a coding model and its tools, and you host it yourself. It runs any frontier or local model behind one interface, and it keeps its records and receipts on your machine. It comes with the Rowan desktop assistant, a coding agent that acts only within the permissions you grant, and fifteen built-in integrations for research, memory and writing. Ten of them ship inside the installer.

Its check-output command grades an answer against the source that decides it. Each accepted result carries a sealed receipt that lists the inputs, the check that ran and its result.

  • Any provider

    Flywheel runs local weights, a local server or any hosted provider you hold a key for, and it sends every answer through the same check. Its list of providers shows whether each key is present and does not display the key itself.

  • A record you can keep

    Receipts are files you keep. Each one carries fingerprints of its contents, so a change to any part of it shows when someone checks it later.

  • Answer locally, escalate the hard part

    Flywheel answers locally, at near-zero cost, when it can check the answer itself. When its checks fail and the attempt budget runs out, it names a stronger model for you to try.

  • Works offline

    With your own weights, Flywheel runs a coding model of just under 9 GB on your machine with no network connection. Hosted models need your keys and a connection.

How an answer gets accepted

A model you choose proposes an answer. A check defined outside the model accepts or rejects it, and the run records the result.

From a proposed answer to a kept receipt

Only the external check can accept an answer, and a failed check sends the model back for more candidates.

  • Bar on the left: the step that decides

Ringed: the external check.

  1. The local model proposes answers. It is cheap and replaceable, and asking it for more candidates widens the pool.
  2. No learned model sits on this step. An external check, such as a test run or a source comparison, accepts or rejects the answer.
  3. A pass writes a receipt named by a fingerprint of its own contents, so anyone can re-check it offline, and a change to any byte makes that check fail.
  4. When the attempt budget runs out below the confidence Flywheel needs, it names a stronger tier, a more capable model you can choose to call. It never calls that tier for you.
  5. Passed answers go into a proof cache with their receipts. The next identical request costs nothing, and the cache re-checks the answer before it serves it.
How we know: the loop drawing
Does not prove
The drawing shows the order of the steps. It does not show that the loop raises accuracy. On the shipped benchmark the verified loop shows no measured accuracy uplift over single-shot, and the interval includes zero.
Method
A model cannot reliably pick its own correct answer, so the check that accepts one sits outside the model. In our runs a self-test added nothing. The external check is the part that can change the outcome, because it can reject an answer, and so a pass carries information. The benchmark further down measured no accuracy gain from the loop. Every accepted answer, cached or fresh, carries the same receipt.

The retired benchmark, kept as history

We retired this comparison on 26 July 2026. Its design let the checked method reuse the single-shot answer, the model's one and only attempt, so its results cannot show whether checking helps.

The model in it is Flywheel Local Coder 14B, just under 9 GB at 4-bit.

Why we retired it
Does not prove
In the retired table, verified inference scored +0.100 above single-shot. The 95 percent interval on that difference is [-0.236, +0.420], which includes zero, and plain best-of-4 sampling tied it. So we do not claim a capability uplift, and the correction below voids the difference as a comparison outright.

Correction
The benchmark ran the baseline as one attempt and the treatment as several, and the treatment's first attempt is the same call as the baseline's only attempt. The treatment therefore cannot score lower. Across all thirteen runs ever made, no task passed the baseline and failed the treatment. That pattern is what one arm containing the other produces, and it carries no evidence of an effect. The quantity measured is verified pass@k, a useful engineering number that says nothing about uplift. Every uplift figure this benchmark produced is void as a comparison for the same reason.
A second finding: artifacts recorded before 26 July 2026 cannot distinguish a model failure from a generation failure that was silently retried. The defect is fixed, and generation failures are now recorded and excluded from the denominator. The older artifacts lack that field, so their per-task failures cannot be re-attributed after the fact.
The model
Flywheel Local Coder 14B is a trained model with a full provenance chain.
What we claim
We claim, and can measure, four things: 100 percent receipt reproducibility, so every accepted answer re-checks; pass parity with the models it routes to; availability on your own schedule, from weights you hold; and local cost. Each claim needs its own evidence, and a limit stated for one claim tells you nothing about the others.
Next measurement
A rebuilt measurement is in progress. It draws the baseline and the treatment from one shared pool of independent attempts, and it adds a compute-matched arm that picks at random and ignores the verifier. It has produced no result yet. If the verifier earns nothing over random selection at the same compute, we will publish that result.

Install Flywheel

Install the Python engine from PyPI with the command below. For the desktop route, download the unsigned Windows installer from the GitHub release. Test a workflow before you depend on it.

pip install flywheel-verify flywheel up

The core package needs nothing beyond the Python standard library. Route online with your keys, or run fully offline against local weights. flywheel up starts Flywheel and prints the address of its page, http://127.0.0.1:8799 by default. Open that address in your browser.

Windows desktop: 1.0.4

Download the Windows x64 installer (about 56 MB), or read the release notes first. The desktop build bundles its own engine, so it needs no Python.

The installer is not code-signed yet, so Windows SmartScreen may warn on first run. Compare its SHA-256 fingerprint with the published one before you run it.

Service Desk Incident Environment 0.2.0

Service Desk Incident Environment is a separately installable product with its own state, action log and verifier. Its offline HTML report keeps four things apart: recorded claims, whether the stored fingerprints still match, recomputed task outcomes, and contradictions between recorded authorization, responses and mutations. Its scripted cases use synthetic data and local HTTP services. They do not call a model provider or connect to ServiceNow.

Extract the sample ZIP and open the passing example first, then the example where a denied change still went through. That second example records a mutation despite denied authorization and an unsuccessful response. Its fingerprints were recomputed so they match, and the report still rejects the contradiction.

To create your own report, use Python 3.11 or newer in a virtual environment. Install a compatible Flywheel engine (the environment requires flywheel-verify >=0.6.1,<0.7), then download the Service Desk 0.2.0 wheel into your current directory. The add-on ships on GitHub. It does not update the desktop app, and this page claims no PyPI listing for it.

python -m pip install ./flywheel_env_service_desk_incident-0.2.0-py3-none-any.whl service-desk-incident-env e2e --out ./incident-runs

The result includes an artifact_dir. Pass that exact run directory, the one inside incident-runs, to verification and review.

service-desk-incident-env verify RETURNED_ARTIFACT_DIR --recompute --json service-desk-incident-env review RETURNED_ARTIFACT_DIR --html-out ./review-output/review.html --json

Open the review page locally. The output must be a new file outside the evidence directory, and review never overwrites an existing file. Review exits 1 when checks fail and 2 for output errors. Inspect the HTML before you share it: the common credential and path redaction does not catch everything, and JSON output keeps local paths.

Does not prove
Matching the wheel hash checks download integrity. Coherent fabricated records can still pass. These checks do not authenticate a producer, measure model alignment, or establish production ServiceNow compatibility.
Limits
The report uses no scripts or external assets and does not execute submitted log actions. Keep the original run artifacts when you investigate a failure. The 0.2.0 source archive is also available.

Reader Flow Review 0.1.0

Reader Flow Review is an experimental standalone skill for reviewing or revising a selected prose passage. It names the main reader-flow issue first and asks for the smallest useful revision. When you ask it to polish, it keeps the author's voice, qualifiers, dialogue and factual uncertainty intact.

Download: Reader Flow Review 0.1.0 skill ZIP, about 6 KB

Extract the ZIP and copy the folder inside it into the skills directory your agent host documents. Invoke it by name when you want a passage critique or a scoped revision. The archive does not install itself or add a marketplace listing.

Use $reader-flow-review to review this passage for reader flow while preserving voice and uncertainty: "The release is useful, but its evidence is developmental. The section should help a reader decide whether to try it without implying the skill verifies facts or certifies publication." Give the dominant reader issue first, then one smallest useful revision.

What stays stable

You can swap the model, the route or the external check. The acceptance criteria you recorded stay the same, and so does the run history, where each run is named by a fingerprint of its contents. A reviewer can then compare a later run with an earlier one on the same task and evidence.
